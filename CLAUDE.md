# CLAUDE.md

STOU is a native macOS app (Swift, SwiftUI, no Xcode project) that
prepares files for their next use. `README.md` is the product spec: it says
what each screen does and marks what is **Today** versus **Planned**.

## Project facts

- Sources live in `Sources/` (`App`, `Engine`, `Models`, `Views`); the bundle's
  `Info.plist` and `plugins.json` live in `Resources/`.
- Build: `scripts/build-app.sh /absolute/path/to/STOU.app` (needs the
  Apple Command Line Tools). `build/` and `*.app/` are ignored.
- `VERSION` is the release series. Every push to `main` publishes a release
  through `.github/workflows/build.yml`: `VERSION` if that tag doesn't exist
  yet, otherwise the next patch. Change `VERSION` only to start a new series.
- This repository is the Homebrew tap. `Casks/stou.rb` is generated by the
  release workflow from `packaging/homebrew/Casks/stou.rb.template`;
  never edit it by hand. `packaging/homebrew/stou` is the `stou`
  command shipped beside the app.
- The app icon's only source is `Resources/AppIcon.appiconset`; the build
  script turns it into `STOU.icns`. Replace the PNGs there to change it.
- STOU was called Rightform. Keep `RightformMigration`, the
  `minimumRightformVersion` key in `plugins.json` (older apps read it) and
  `packaging/homebrew/cask_renames.json` until no Rightform installs remain.
- When behaviour changes, update the matching section of `README.md` in the
  same change, and keep its Today/Planned labels honest.

## Scope

- Keep changes close to the request. Don't add features, refactor neighbouring
  code, or reformat and rename unrelated files as part of a narrow change.
- Mention useful but unrequested improvements separately instead of mixing
  them in.
- If the task is ambiguous, take the safest reasonable reading and state it;
  ask only when the ambiguity blocks the work.

## Implementation

- Read the surrounding code and its callers before editing.
- Match the existing style; reuse existing helpers, views and patterns before
  adding new ones. No speculative abstractions or new dependencies.
- Preserve existing behaviour unless the task changes it. When local patterns
  conflict, follow the most local, recent and actively used one and say so.

## Git

- Check the branch and working tree before changing anything.
- Prefer a branch and a pull request for non-trivial work. Every push to
  `main` ships a release to users, so push or merge there only when asked.
- No destructive git actions (force push, history rewrites on shared
  branches, discarding work) without explicit approval.
- Keep commits grouped by logical step.

## Verification

- Verify before calling work done: build with `scripts/build-app.sh`, and for
  behaviour or UI changes run the app and check the result in it.
- Static inspection does not prove UI correctness; say whether a change was
  checked in the running app or only read.
- Never claim a check passed if it wasn't run; name skipped checks.

## Reporting

Say what changed, what was verified, what is still uncertain and which checks
were skipped. On longer tasks, summarise after meaningful steps; if the state
becomes unclear, stop and restate it before continuing.

## Product and UX

- Describe behaviour as what the user sees and what happens after each
  action, covering default, empty, loading, error, success and disabled
  states and edge cases.
- Before a non-trivial UI change, pin down the primary workflow, available
  space and window sizes, existing patterns and terminology, and what must
  stay stable. When feedback reveals a wrong constraint, redesign coherently
  instead of patching symptoms.
- Every visible element must serve a task or state. Prefer, in order:
  removing UI, native macOS behaviour, an existing pattern, fixing an existing
  value, and only then something new.
- Check structure (grouping, hierarchy, reading order, alignment, spacing)
  with realistic content before polish. Long values, truncation, errors and
  disabled states must stay understandable and recoverable.
- Accessibility: every control has an accessible name, keyboard access and a
  practical hit area; meaning never relies on colour or motion alone; respect
  system accessibility settings.
- Preserve user agency: cancelling, going back and leaving a guided flow are
  always easy. Use progressive disclosure rather than hiding important things.
- Feedback stays next to what it describes; alerts are for critical,
  actionable information only. Don't celebrate routine success.
- Failures say what failed, why, and how to recover, and consequential
  messages are never auto-dismissed.
- Important actions never exist only as a gesture, hover, drag-and-drop,
  colour, sound or animation.

Prefer a simple correct solution over a clever broad one.
